# Customer Management Service — System Specification

## 1. Purpose

This document defines the precise system behavior for the Customer Management Service.

It refines the business requirements defined in `01-requirements.md` so that expected application behavior is clear and unambiguous.

---

## 2. Customer Data Specification

Each customer must contain the following information:

| Field | Specification |
|---|---|
| Customer ID | System-generated, unique, and immutable |
| First Name | Required and non-blank |
| Last Name | Required and non-blank |
| Email | Required, valid format, and unique using case-insensitive comparison |
| Phone Number | Required and non-blank |
| Status | ACTIVE or INACTIVE |
| Created At | Generated when the customer is created |
| Updated At | Updated whenever customer information changes |

---

## 3. Create Customer Behavior

When creating a customer:

1. First name, last name, email, and phone number must be provided.
2. Required values must not be blank.
3. Email must have a valid format.
4. Email must be unique using a case-insensitive comparison.
5. A new customer must default to `ACTIVE` status.
6. Customer ID must be generated by the system.
7. Created At and Updated At must be generated when the customer is created.
8. Invalid customer data must be rejected.
9. A duplicate email address must be rejected.

---

## 4. Retrieve Customer by ID Behavior

When retrieving a customer by ID:

1. If the customer exists, the customer information must be returned.
2. If the customer does not exist, the system must produce a not-found outcome.

---

## 5. Retrieve All Customers Behavior

When retrieving all customers:

1. All existing customers must be returned.
2. If no customers exist, an empty collection must be returned.

---

## 6. Update Customer Behavior

When updating an existing customer:

1. First name, last name, email, phone number, and status may be updated.
2. Customer ID must remain unchanged.
3. Created At must remain unchanged.
4. Updated At must be refreshed when customer information changes.
5. Required customer information must remain present and non-blank.
6. Email must remain valid and unique using a case-insensitive comparison.
7. A customer may retain their own existing email address.
8. An email address belonging to another customer must be rejected.
9. Status must be either `ACTIVE` or `INACTIVE`.
10. Invalid customer data must be rejected.
11. If the customer does not exist, the system must produce a not-found outcome.

---

## 7. Delete Customer Behavior

When deleting a customer:

1. If the customer exists, the customer must be deleted.
2. If the customer does not exist, the system must produce a not-found outcome.

---

## 8. Business Rule Specifications

### BR-01 — Unique Email

Customer email addresses must be unique using a case-insensitive comparison.

For example, the following email addresses are considered the same:

- `customer@example.com`
- `Customer@Example.com`

A customer may retain their own email address during an update.

An email address already assigned to another customer must not be accepted.

### BR-02 — Required Customer Information

The following customer information is required:

- First Name
- Last Name
- Email
- Phone Number

Required values must not be blank.

Email must have a valid format.

### BR-03 — Customer Status

Customer status must be one of:

- `ACTIVE`
- `INACTIVE`

New customers must default to `ACTIVE`.

### BR-04 — Non-Existing Customer

If an operation targets a customer that does not exist, the system must produce a not-found outcome.

---

## 9. Audit Timestamps

The system must maintain:

- `Created At` — generated when the customer is created and never changed.
- `Updated At` — generated when the customer is created and refreshed whenever customer information changes.

---

## 10. Specification Outcome

This specification defines the expected system behavior for the Customer Management Service.

The next step is to convert these behaviors into explicit and testable acceptance criteria.
